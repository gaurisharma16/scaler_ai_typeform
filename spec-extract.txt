respondent screen (same dark theme, scaled down).
Dashboard  is light canvas, card grid of forms (thumbnail, title, status
pill, response count), a "Create form" primary button top-right.

from your screen recording): a free-form node canvas, not a list. Each
question renders as a small draggable card (number badge + type icon +
title) positioned anywhere on a dotted-grid canvas. Cards connect via
curved bezier arrows drawn from a small dark circular connector handle
on one card to the next, and the arrows redraw live as cards are dragged.

Build the Workflow canvas with React Flow  (@xyflow/react ) rather than hand-
rolled SVG + drag math — it natively gives draggable nodes, animated bezier
edges that reroute on drag, a dot-grid background, minimap, and zoom/pan. Each
question = one React Flow node; the default linear sequence = one edge per
consecutive pair; a branching rule (bonus) adds a second edge with a condition
label.
2. Tech stack
Frontend : Next.js 14 (App Router) + TypeScript, T ailwind CSS, framer-
motion for transitions, @dnd-kit/core  for drag-and-drop reordering, 
@xyflow/react  for the Workflow canvas, react-hook-form  + zod for
validation.
Backend : FastAPI (Python), SQLAlchemy ORM, Pydantic schemas,
Alembic for migrations (optional, nice for the DB-design grade).
Database : SQLite for dev (per assignment); schema should be ORM-
portable to Postgres.
Auth : none — single hardcoded "default creator" (per assignment's
simplification note). All /forms endpoints operate implicitly as that
creator.

responses , responses 1—N answers , questions 1—N answers . 
answers.value_json  keeps one flexible answer shape instead of a
column per question type, which is what lets the summary-stats endpoint
work generically across types.

4. API design (FastAPI)
Creator/builder side (implicit default creator, no auth header needed)
GET    /api/forms                        list forms + status + response_count
POST   /api/forms                        create form (title)
GET    /api/forms/{id}                   full form + questions
PATCH  /api/forms/{id}                   rename / theme / welcome / thank-you text
POST   /api/forms/{id}/duplicate         clone form + its questions
DELETE /api/forms/{id}
POST   /api/forms/{id}/publish
POST   /api/forms/{id}/unpublish
POST   /api/forms/{id}/questions         create question
PATCH  /api/questions/{id}               edit question
DELETE /api/questions/{id}
POST   /api/forms/{id}/questions/reorder  body: [question_id,...] in new order
PATCH  /api/questions/{id}/position       body: {canvas_x, canvas_y} (Workflow drag)
GET    /api/forms/{id}/logic              list edges for the Workflow canvas
POST   /api/forms/{id}/logic              create an edge (from_question_id, to_question_id, condition)
DELETE /api/logic/{id}
GET    /api/forms/{id}/responses         list responses (table view)
GET    /api/responses/{id}               single response w/ answers
GET    /api/forms/{id}/summary           per-question aggregates
GET    /api/forms/{id}/responses/export  CSV (bonus)
Public respondent side (no auth, slug-based)
GET    /api/public/forms/{slug}          published form + ordered questions
POST   /api/public/forms/{slug}/responses          start a response -> response_id
PATCH  /api/public/responses/{response_id}/answers  upsert one answer per question
                                                      (server validates per type)
POST   /api/public/responses/{response_id}/complete  mark completed_at
Splitting "start response" from "submit answer" is what enables the
bonus partial-response tracking: a response row exists as soon as the
respondent lands on question 1, updates as they go, and completed_at
stays null if they drop off.
Validation lives in Pydantic schemas: required  fields reject empty values,
email type validates format, number type validates numeric + optional

===== PAGE 9 =====
Core features:
1. Form builder: 3-pane layout (question list w/ drag-and-drop reorder,
   center editor for the active question, right live preview styled like
   the real respondent screen). Question types: short text, long text,
   multiple choice, dropdown, email, number, yes/no, rating. Each
   question has required toggle + optional description.
2. Form management: list with status + response count, create/rename/
   duplicate/delete, publish/unpublish generates a public /f/{slug} link.
2b. Workflow tab: a React Flow canvas showing each question as a
   draggable card (number badge, type icon, title) connected by curved
   bezier arrows that reroute live as cards are dragged; drag position
   persists via PATCH /questions/{id}/position; default edges follow
   question order, editable via the logic_rules table (basic conditional
   branching is a bonus, not required to pass).
3. Respondent flow: full-screen, one question at a time, dark theme,
   keyboard nav (Enter to advance, up/down arrows for prev/next), thin
   progress bar, client + server validation, submit -> thank-you screen,
   no auth required.
4. Results: table of responses per form, single-response detail view,
   per-question summary stats (counts for choice-type questions, etc.),
   CSV export (bonus).
5. Seed the DB with 2 published forms (mixed question types) with 10-20
   responses each, plus 1 draft form.
